**Subject:** `D:\Minecraft\1.20forge\confluence\PortLib` (`archivesName = "MesdagPortLib+neoforge1.21.1 to forge1.20.1"`, `PortLib\build.gradle:20`).
Read-only audit — **no project file was modified**; this note is the only file created.

**Ground truth used (no guessing):**

* Every PortLib declaration was read from `PortLib\src\main\java\org\mesdag\portlib\**` (627 `.java` files, 29 617 lines) with the `read`/`grep`/`glob` tools, plus the non-Java artifacts listed in §2/§3.
* Every "native NeoForge 1.21.1" claim was checked against the **extracted NeoForge 21.1.219 / MC 1.21.1 sources** already on this machine at
  `D:\Minecraft\1.21neoforge\confluence\build\_nfsrc_219\` (paths quoted as `net/neoforged/neoforge/...`), and cross-checked against `neoforge-21.1.170-sources.jar` in the Gradle cache.
* Consumer-side evidence from the 1.20.1 mod sources: `ConfluenceOtherworld\src\main\java` (2 496 `.java`, **474 files import `org.mesdag.portlib.*`**), `Confluence-Magic-Lib`, `TerraCurio`, `TerraFurniture`.

**Classification vocabulary** (exactly one per type):

| Bucket | Meaning |
|---|---|
| `EMULATION-ONLY` | Exists only because 1.20.1 lacks the feature. A 1.21.1 build needs nothing, or an import-satisfying empty stub. |
| `FACADE` | Wrapper/alias of an API that exists natively in NeoForge 1.21.1. Becomes a thin delegation; **the native target is named in every row**. |
| `SHARED-PLAIN` | Loader-independent utility/abstraction, copyable to 1.21.1 unchanged. |
| `UNKNOWN` | Needs a human decision — reason given in one clause. |

**Row convention.** 627 files cannot be tabulated one row per file without burying the signal, so where a package consists of mechanically identical 1-line delegations the row is grouped as `group (N files)` with a representative path; the group contributes **N** to the §4 counts. Every `IPort*`/`IPort*Extension` interface, every top-level `network`/`registries`/`diff` type, and every name-mismatched event is listed individually.

# 2. Extensions & injection

## 2.1 Compile-time: `portlib-interfaceinjection.json`

`PortLib\portlib-interfaceinjection.json` (236 lines) is a Forge/moddev **interface-injection** manifest: a JSON object mapping 82 target classes (FQN with `/`) to the list of interfaces the compiler (and the runtime patcher) must consider present:

```json
"net/minecraft/world/item/ItemStack": ["org/mesdag/portlib/wrapper/common/extensions/IPortItemStackExtension"],
"net/minecraft/world/item/Item":      ["org/mesdag/portlib/wrapper/common/extensions/IPortItemExtension"],
"net/minecraftforge/registries/IForgeRegistry": ["…/IPortForgeRegistryExtension"]   // :128
```

* Consumed downstream via `interfaceInjectionData(...)` — `ConfluenceOtherworld\build.gradle:197`, `TerraFurniture\build.gradle:113`, `TerraCurio\build.gradle:139`, `Confluence-Magic-Lib\build.gradle:108`. PortLib also publishes it as a Gradle module-metadata variant (`PortLib\build.gradle:161-203`).
* Targets are **vanilla** (`ItemStack`, `Block`, `Level`, `Entity`, `Holder`, `Registry`, `MappedRegistry`, `ResourceLocation`, `FriendlyByteBuf`, `GuiGraphics`, `AABB`, `AdvancementProgress`, `ChunkAccess`, …), **Blaze3D** (`com/mojang/blaze3d/vertex/VertexConsumer` — a library class mixin cannot reach) and **loader** classes (`IForgeRegistry`, `ForgeConfigSpec$ConfigValue`, `FluidType$Properties`) — lines 116-133.
* Because injection is a *compile-time promise*, mod code can write `IPortItemStackExtension.of(stack).getTool()` or cast `(IPortAttachmentHolder) player` (`ConfluenceOtherworld\...\attachment\LeftClickState.java:13`). It also generates a helper class per injected interface for its **static** members, which PortLib itself imports: `PortLib.extensions.net.minecraftforge.registries.IForgeRegistry.PortIForgeRegistryExtension` (`registries\PortRegistryMaker.java:3`), `PortLib.extensions.com.mojang.serialization.Codec.PortCodecExtension` (`IPortItemStackExtension.java:3`), `PortLib.extensions.com.mojang.serialization.DataResult.PortDataResultExtension` (`PortRegistryEntry…`/`PortParticleTypeRegistration.java:3`).
* **1.21.1 equivalent:** NeoForge's own `net.neoforged.neoforge.common.extensions.I*Extension` interfaces already exist for the same targets (`IItemStackExtension`, `IBlockExtension`, `IEntityExtension`, `ILivingEntityExtension`, `IPlayerExtension`, `ILevelExtension`, `IHolderExtension`, `IHolderSetExtension`, `IHolderLookupProviderExtension`, `IRegistryExtension`, `IFriendlyByteBufExtension`, `IMobEffectExtension`, `IAttributeExtension` — all verified present). A 1.21.1-native PortLib therefore keeps the *same* JSON mechanism (`interfaceInjectionData` is a NeoForge moddev feature too) but points each entry at a `Port*Extension` interface whose `default` methods delegate to the native one. The 78 `IPort*Extension` files survive as the **shared vocabulary**, with their bodies reduced to delegation.

## 2.2 Runtime: `coremods/portlib_extension_insert.js` (36 lines)

Registered by `src\main\resources\META-INF\coremods.json` (`{"portlib_extension_insert": "coremods/portlib_extension_insert.js", "portlib_insert": "coremods/portlib_insert.js"}`). It is a single generic `transformer(target, extension)` that, for a `CLASS` target, does:

```js
if (!node.interfaces.contains(extension)) node.interfaces.add(extension);   // :30-32
```

i.e. it appends the interface in TSV/ASM at class-load time. It covers the **17 targets mixins cannot patch** (Blaze3D + core Java/loader classes): `VertexConsumer`, `Holder`, `IdMap`, `RegistryAccess`, `HolderLookup$Provider`, `Registry`, `IForgeRegistry`, `ForgeConfigSpec$ConfigValue`, `SearchTree`, `HolderSet`, `ParticleOptions`, `DataProvider`, `StringRepresentable`, `Recipe`, `BlockEntityRenderer`. Two concrete defects worth knowing before porting:

1. **Dead/duplicated entry:** `'block_entity_renderer'` is declared twice (lines 5 and 18). The JS object literal keeps the last, so line 5 is dead; and its interface `IPortBlockRendererExtension` **does not exist** in `wrapper\common\extensions\` (verified — only `IPortBlockEntityRendererExtension` does). Line 18's spelling is the one used.
2. The whole file is unnecessary on 1.21.1: NeoForge ships its extension interfaces on those same classes, so a 1.21.1 PortLib drops this script and the `coremods.json` entry.

# 5. Risks / things that cannot be shared

**R1 — Events cannot be "thin-delegated" at all; a translation layer must survive.** NeoForge fires *its* event classes. Mod code registers listeners by *Port* class name, so every Port-named event must be re-posted by PortLib, which is exactly what `PortEventHooks.wrapEvent` does today against Forge (`event\PortEventHooks.java:150-180`; wrapper factories built reflectively at `:91-148`; each Port event self-registers in a static initializer, e.g. `event\entity\player\PortPlayerInteractEvent.java:74-76`). Consequence: `PortEvent`, `PortEventHooks`, `PortEventHandler`, `PortBus` are **not** removable under the "identical source" goal (they are classified FACADE here; a reviewer who reads EMULATION-ONLY as "no 1.20.1 Forge event to wrap" would put these four there — that is the one genuine classification judgement call in this report). What *is* removable is `PortBus.unwrap`'s Forge plumbing: on 1.21.1 the mod bus is `ModContainer#getEventBus()` and the game bus is `NeoForge.EVENT_BUS`.

**R2 — Every `Port*Event` name is a source-visible alias, and some differ beyond the prefix.** 55 of the 71 named-type wrappers are exactly `"Port" + nativeName`; the rest are not, and 14 nested enums/interfaces are renamed too. Concrete mismatches that a naive "strip `Port`" port gets wrong: `PortFinalizeSpawnEvent`→`FinalizeSpawnEvent` (Forge nested `MobSpawnEvent.FinalizeSpawn` → native top-level); `PortSpawnClusterSizeEvent`→`SpawnClusterSizeEvent` (Forge `LivingPackSizeEvent`); `PortRegisterSpawnPlacementsEvent`→`RegisterSpawnPlacementsEvent` (Forge `SpawnPlacementRegisterEvent`); `PortBlockGrowFeatureEvent`→`BlockGrowFeatureEvent` (Forge `SaplingGrowTreeEvent`); `PortCreateFluidSourceEvent`→`CreateFluidSourceEvent` (Forge nested `BlockEvent.CreateFluidSourceEvent` → native top-level, different package); `PortItemEntityPickupEvent.Pre/Post` (Forge `EntityItemPickupEvent` / `PlayerEvent.ItemPickupEvent`); `PortRegisterGuiLayersEvent`→`RegisterGuiLayersEvent` (Forge `RegisterGuiOverlaysEvent`); `PortRenderFrameEvent`→`RenderFrameEvent` (Forge `TickEvent.RenderTickEvent`); `PortTextureAtlasStitchedEvent`→`TextureAtlasStitchedEvent` (Forge `TextureStitchEvent.Post`); `PortFMLClientSetupEventPort` — the only `Port` **suffix**. Nested renames that mod code names verbatim: `PortMobEffectEvent.Applicable.PortResult.DO_NOT_APPLY` (`ConfluenceOtherworld\...\LivingEntityEvents.java:399`), `PortPlayerInteractEvent.LeftClickBlock.PortAction.START` (`…\PlayerEvents.java:176`), `PortResult`/`PortAction`/`PortUsePhase`/`PortProgressType`/`PortNote`/`PortOctave`/`PortPistonMoveType`/`PortLivingTargetType`/`PortUpdateCause`/`PortRegisterHelper`/`PortNewRegistry`.

**R3 — Package paths differ even where class names match.** Native root-level events live in `net.neoforged.neoforge.event.*`, while PortLib puts 21 of them in `event.other`; `PortRegisterPayloadHandlersEvent`/`PortRegisterConfigurationTasksEvent` are native `…network.event`; `PortRegisterDataMapTypesEvent`/`PortDataMapsUpdatedEvent` are native `…registries.datamaps`; `PortStatAwardEvent` is native root; `PortRegisterCapabilitiesEvent` is native `…capabilities`; `extensions\common\PortRegisterClientExtensionsEvent` is native `client.extensions.common` (no `event` segment). Wildcard imports in mod code (`import org.mesdag.portlib.event.client.*;`, `…event.entity.living.*;`, `…event.entity.player.*;`) mean the package layout must be reproduced exactly or those imports silently stop resolving names.

**R4 — `PortEventHandler.addListener(...)` vs `@EventBusSubscriber`/`NeoForge.EVENT_BUS`.** This one is *good news*: the four overloads (`event\PortEventHandler.java:14-28`) map 1:1 onto `net.neoforged.bus.api.IEventBus#addListener`, including the reflective event-type inference (`TypeResolver.resolveRawArgument`, :31-37), and the mod uses **no** `@SubscribeEvent`/`@EventBusSubscriber` anywhere (verified over 2 496 files) — it registers 170+ listeners through `PortEventHandler.addListener`, e.g. `ConfluenceOtherworld\...\client\event\GameClientEvents.java:103-105`, `…\common\event\game\entity\PlayerEvents.java:30+`. `PortEventPriority` → `net.neoforged.bus.api.EventPriority`. The remaining hazard is `postEvent` (`:44-50`): it picks the bus with `event instanceof IModBusEvent` and, for the mod bus, resolves the *caller's* mod id from `PortEnvironment.getCallerModId()` — on 1.21.1 that must become the per-`ModContainer` bus, and 16 of the 62 client events are missing the `IPortModBusEvent` marker their natives carry, so they would be posted to the **wrong bus** and silently never fire.

**R5 — `ResourceLocation` ids vs `ResourceKey`.** PortLib keeps 1.20.1-style id-keyed APIs in places where 1.21.1 is key-keyed: `PortRegistration.register(name, supplier)` builds `ResourceLocation.fromNamespaceAndPath(...)` (`registries\PortRegistration.java:42-52`), `PortCustomRegistration.get(ResourceLocation)`/`getKey(R)` (`:47-62`), `PortAttachmentRegistration`/`PortDataComponentRegistration` `register(String, …)` (`registries\PortAttachmentRegistration.java:15`, `PortDataComponentRegistration.java:17`), and `PortDataMapType`/`PortDataMapProvider` are id-based where `DataMapType.builder(id, registryKey, codec)` is verified to take both. Mod code uses both styles (53 hits for `ResourceKey<Registry`/`fromNamespaceAndPath`), e.g. `ConfluenceOtherworld\...\init\ModDataComponentTypes.java:17` (`TYPES.builder("loot", …)`) and `PortDataMapProvider`. Native 1.21.1 `DeferredRegister`/`DeferredHolder` are `ResourceKey`-first; a delegation layer must bridge by constructing keys at the boundary, and mod code that stores/compares ids (`PortRegistryEntry.getId()`, `IPortMappedRegistry.portlib$resolve`) needs the Port spelling kept.

**R6 — Data components vs NBT/capabilities: same method names, different types.** `IPortItemStackExtension.get/set/remove/has/getOrDefault(PortDataComponentType<T>)` (:710-760) is a structural match for 1.21.1 `ItemStack` component accessors, and `PortDataComponentType.Builder.persistent(Codec)/networkSynchronized(StreamCodec)` is method-identical to native `DataComponentType.Builder`. The break is the **type name** and the backing store: PortLib's maps are NBT-backed (`PortPatchedDataComponentMap`, `diff\component\…`; `IPortItemStack`'s `DATA_COMPONENTS`/`portlib:data_components`, `portlib:custom_data`, `portlib:fire_resistant`, `portlib:enchantment_glint_override`, `portlib:intangible_projectile` tags at `IPortItemStackExtension.java:196-497`) and capability-backed (`CapabilityProviderAccessor.callSerializeCaps()` at `:788`). Mod code imports `PortDataComponentType`/`PortDataComponentMap`/`PortDataComponentPatch` (`ConfluenceOtherworld\...\common\component\BulletPropertyComponent.java:7,48`, `...\init\ModDataComponentTypes.java:7,17`) — those imports must survive, but the NBT shim layer can go. Attachments are the mirror image: `((IPortAttachmentHolder) player).getAttach(ModAttachmentTypes.LEFT_CLICK_STATE)` (`ConfluenceOtherworld\...\common\attachment\LeftClickState.java:13`) becomes `player.getData(...)` natively — a **method rename**, not just a type rename (`getAttach`→`getData`, `setAttach`→`setData`, `hasAttach`→`hasData`, `getExistingAttachOrNull`→`getExistingDataOrNull`, `syncAttach`→`syncData`; all verified in `IAttachmentHolder.java`).

**R7 — Two outright signature breaks in shared source (compile errors, not warnings).** `event\client\PortCalculatePlayerTurnEvent`: PortLib exposes `PortTriState getCinematicCameraEnabled()/setCinematicCameraEnabled(PortTriState)` and ctor `(double)`; native (`CalculatePlayerTurnEvent`, both 21.1.170 and 21.1.219) uses **`boolean`** and ctor `(double, boolean)`. `event\client\PortRenderLivingEvent<T, M, E extends RenderLivingEvent<T,M>>` has **3** type parameters, native `RenderLivingEvent<T,M>` has **2**. Also `getPartialTick()` returns `PortDeltaTicker` in PortLib vs `net.minecraft.client.DeltaTracker` natively across `CustomizeGuiOverlayEvent`, `RenderGuiEvent`, `RenderFrameEvent`, `RenderLevelStageEvent`, `RenderGuiLayerEvent`; `RenderNameTagEvent`/`CalculatePlayerTurnEvent` use `PortTriState` where native uses `net.neoforged.neoforge.common.util.TriState`; `RegisterGuiLayersEvent`/`RenderGuiLayerEvent` use `PortGuiLayer` where native uses `LayeredDraw.Layer`; `PortAttributeTooltipContext`↔`AttributeTooltipContext`, `PortEquipmentSlotGroup`↔`EquipmentSlotGroup`, `PortQuadLighter`↔`QuadLighter`, `PortAttributeModifier`↔`AttributeModifier`.

**R8 — Renames where the native spelling is different, and the mod imports the Port one.** Verified against 21.1.219: `PortDataMapType`→`DataMapType`, `PortDataComponentType`→`DataComponentType`, `PortDataComponentMap`→`DataComponentMap`, `PortDataComponentPatch`→`DataComponentPatch`, `PortConfigSpec`→`ModConfigSpec` (value classes already match), `PortWidgetSprites`→`WidgetSprites`, `PortRegistries`→`NeoForgeRegistries`, `PortDeltaTicker`→`DeltaTracker` (**not** `RenderTickCounter`, which does not exist in 1.21.1), `PortGuiLayer`→`LayeredDraw.Layer`, `PortConfigurationScreen`→`neoforge.client.gui.ConfigurationScreen`, `IPortAttachmentHolder`→`IAttachmentHolder`, `PortCustomIngredient`→`ICustomIngredient` (verified: there is **no** vanilla `CustomIngredient` in 1.21.1), `PortIngredientType`→NeoForge `common.crafting.IngredientType`, `PortTriState`→`net.neoforged.neoforge.common.util.TriState` (**not** vanilla `net.minecraft.util.TriState`, which is 1.21.2+), `PortAdvancedAddEntityPayload`→`AdvancedAddEntityPayload`, `PortSyncAttachmentsPayload`→`SyncAttachmentsPayload`, `PortKnownRegistryDataMapsPayload`→`KnownRegistryDataMapsPayload`.

**R9 — Version drift inside "1.21.1".** Three PortLib types mirror features that landed *after* 1.21.1 and must therefore stay PortLib-local: `PortArmorItem.PortType` (native `net.minecraft.world.item.equipment.ArmorType` is 1.21.2+; in 1.21.1 `ArmorMaterial` is a record at `net.minecraft.world.item.ArmorMaterial` — verified), `IPortAttributeExtension.Sentiment` (`Attribute.Sentiment` is 1.21.2), and `IPortAbstractArrow`'s pickup/`firedFromWeapon` shape. Also `PortBundledPacket` has no native twin (`ClientboundBundlePacket` is a different mechanism), and `PortRegistryEntry.Memoized` has none either.

**R10 — `accesstransformer.cfg` (44 lines) will not carry over.** It widens 30+ 1.20.1-specific members (`ItemStack.f_41586_ LORE_STYLE`, `m_41626_ shouldShowInTooltip`, `PotionBrewing.m_43502_ addContainerRecipe`, `ChunkMap.f_140150_ entityMap`, `Explosion.f_46010_ blockInteraction`, `TextureAtlas.f_118264_ texturesByName`, `SimpleContainer.f_19147_ items`, `BlockEntityType.f_58915_ validBlocks`, …). SRG names and several members changed in 1.21.1 (e.g. `BundleItem.getContents`, `SuspiciousStewItem.listPotionEffects`, `DataFixTypes.currentVersion`); the file must be re-derived, and each AT exists to serve a mixin, so most disappear with the mixins.

**R11 — Version constraint on the shared source.** Because the mod's `neoforge.mods.toml`/`mods.toml` and dependency ranges differ (`PortLib\gradle.properties:28-30`, `forge_version_range` vs `neoforge` range) and because `PortLib.java`'s constructor signature is `(FMLJavaModLoadingContext)` (1.20.1 Forge) versus the 1.21.1 `@Mod` constructor style (no-arg or injected `IEventBus`/`ModContainer`), the entrypoint file cannot be literally identical; only the `org.mesdag.portlib.*` API surface can.
